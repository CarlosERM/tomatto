# 🍅 Tomatto

A simplified [Cold-Turkey-style](https://wwwgetcoldturkey.com/) website blocker built as the practical exercise for **Unidade III — GenAI applied to software testing**: two REST services that integrate over HTTP, a Manifest V3 browser extension that consumes them, and an integration-test suite whose test cases were generated by four deliberately different LLM prompt types.

## Resumo (PT-BR)

O Tomatto bloqueia sites no navegador sem interface: você cadastra domínios na **Manager API** (`:3001`), que persiste em SQLite e envia um snapshot completo (com versão monotônica) para a **Sync API** (`:3002`) via HTTP — integração REST-to-REST real, com fila de pendências (`sync_status="pending"`) e retry quando a Sync está fora do ar. Uma extensão Chrome (MV3) faz polling da Sync API a cada minuto usando o handshake ETag/304 e aplica o bloqueio com `declarativeNetRequest`, redirecionando para uma página local.

Os casos de teste de integração foram produzidos por **quatro tipos de prompt** (`prompts/`): contrato (a partir do spec OpenAPI), cenários ponta a ponta, casos adversariais entre serviços e geração de dados de teste. As transcrições brutas da LLM ficam em `generated-tests/` e os testes executáveis curados em `tests/integration/` (43 testes, todos marcados `integration`).

## Architecture

```
┌───────────────┐ 1. persist + bump version   ┌────────────────────────┐
│  Manager API  │ ───────────────────────────►│ SQLite: rules          │
│    :3001      │                             │ {id, domain,           │
│               │ 2. write-through push       │  include_subdomains,   │
│ POST /rules   │  (full snapshot + version)  │  created_at,           │
│ GET  /rules   │ ────────────────┐           │  sync_status}          │
│ DELETE /rules │                 │           └────────────────────────┘
│ POST /sync/   │    fails? rule stays        │
│    retry      │    "pending" → retry later  │
└───────────────┘                 ▼
                       ┌──────────────────────┐  GET /blocked          ┌─────────────────┐
                       │      Sync API        │ ◄──────────────────────│ Chrome ext (MV3)│
                       │        :3002         │ ──► {version, sites[]} │ chrome.alarms   │
                       │ stores latest        │    weak ETag W/"v"     │ 1 min poll +    │
                       │ snapshot; rejects    │    If-None-Match→304   │ onInstalled     │
                       │ stale versions (409) │                        │ dNR → blocked.  │
                       └──────────────────────┘                        │    html         │
                                                                       └─────────────────┘
```

**Integration seams under test:** Manager→Sync write-through push · version monotonicity across services · ETag/304 consumer handshake · outage/pending/retry eventual consistency · SQLite persistence across restarts.

## Repo layout

| Path | What it is |
|------|------------|
| `services/manager_api/` | FastAPI service owning the block list (write-through to Sync) |
| `services/sync_api/` | FastAPI read-only snapshot service with ETag/304 polling |
| `services/shared/` | Domain normalization + SQLite stores |

| `generated-tests/` | Raw LLM transcripts (evidence), one file per run |
| `tests/integration/` | Curated executable suite (`pytest -m integration`) |

## Getting started

```bash
uv sync                      # or: pip install -r requirements.txt

# terminal 1 — Sync API first (Manager pushes to it)
uv run uvicorn services.sync_api.main:sync_app --port 3002

# terminal 2 — Manager API
uv run uvicorn services.manager_api.main:manager_app --port 3001

# try it
curl -X POST localhost:3001/rules -H 'content-type: application/json' \
     -d '{"domain": "https://www.reddit.com/"}'
curl -i localhost:3002/blocked    # note the ETag header; repeat with If-None-Match → 304
```

**Load the extension:** `chrome://extensions` → Developer mode → *Load unpacked* → select `extension/`. Within a minute (or on reinstall/browser restart) it fetches the list and blocked domains redirect to a local 🍅 page. On WSL2, Windows Chrome reaches the WSL servers via `localhost` forwarding out of the box.

## Running the tests

```bash
uv run pytest -m integration          # everything (~2s)
uv run pytest tests/integration/test_p3_negative.py -v   # one prompt's lineage
```

Four modules mirror the four prompt types; `test_smoke_real_servers.py` boots both services as real uvicorn subprocesses and drives them over actual HTTP.

## Prompt adjustment notes (fill in after running the prompts)

Observations that drove each v1 → v2 refinement are documented inside the prompt files. After you run them with your LLM, record what *your* runs showed here:

- **P1:** *(e.g., v1 hallucinated endpoints; anchoring to "ONLY fields present in the spec" fixed it — did yours?)*
- **P2:** *(v1 produced shallow single-service happy paths; naming both services per scenario forced real integration flows)*
- **P3:** *(v1 stopped at HTTP-level 400s; enumerating cross-service failure classes unlocked outage/retry cases)*
- **P4:** *(v1 gave boring domain lists; demanding JSON + expected normalized form made output directly executable — and surfaced a real normalization-equivalence bug: `example.com.` ≡ `example.com` → duplicate must 409)*
- **Live finding (post-suite):** none of the four prompt types covered the *consumer-side* contract, and reality filled the gap: the extension installed zero rules because `declarativeNetRequest` rejects a relative `redirect.extensionPath` (`"blocked.html"` → *"specifies an incorrect value"*), and even absolute paths need `web_accessible_resources` before Chrome will navigate to them. A would-be **P5 prompt** ("generate contract checks between the Sync API response and the browser's declarativeNetRequest rule schema") is the lesson: GenAI tested every seam we described, but seams we didn't describe stay untested until probed — arguably the strongest argument for treating prompts as a *coverage plan*.
