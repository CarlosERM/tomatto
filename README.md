# 🍅 Tomatto

A simplified [Cold-Turkey-style](https://wwwgetcoldturkey.com/) website blocker built as the practical exercise for **Unidade III — GenAI applied to software testing**: two REST services that integrate over HTTP, a Manifest V3 browser extension that consumes them, and an integration-test suite whose test cases were generated by four deliberately different LLM prompt types.

## Resumo (PT-BR)

O Tomatto bloqueia sites no navegador sem interface: você cadastra domínios na **Manager API** (`:3001`), que persiste em SQLite e envia um snapshot completo (com versão monotônica) para a **Sync API** (`:3002`) via HTTP — integração REST-to-REST real, com fila de pendências (`sync_status="pending"`) e retry quando a Sync está fora do ar. Uma extensão Chrome (MV3) faz polling da Sync API a cada minuto usando o handshake ETag/304 e aplica o bloqueio com `declarativeNetRequest`, redirecionando para uma página local.

Os casos de teste de integração foram produzidos por **quatro tipos de prompt** (`prompts/`): contrato (a partir do spec OpenAPI), cenários ponta a ponta, casos adversariais entre serviços e geração de dados de teste. As transcrições brutas da LLM ficam em `generated-tests/` e os testes executáveis curados em `tests/integration/` (43 testes, todos marcados `integration`).

## Architecture

```
┌───────────────┐ 1. persist + bump version   ┌────────────────────────┐
│  Manager API  │ ───────────────────────────►│ SQLite: rules          │
│    :3001      │                             │ {id, domain,           │
│               │ 2. write-through push       │  include_subdomains,   │
│ POST /rules   │  (full snapshot + version)  │  created_at,           │
│ GET  /rules   │ ────────────────┐           │  sync_status}          │
│ DELETE /rules │                 │           └────────────────────────┘
│ POST /sync/   │    fails? rule stays        │
│    retry      │    "pending" → retry later  │
└───────────────┘                 ▼
                       ┌──────────────────────┐  GET /blocked          ┌─────────────────┐
                       │      Sync API        │ ◄──────────────────────│ Chrome ext (MV3)│
                       │        :3002         │ ──► {version, sites[]} │ chrome.alarms   │
                       │ stores latest        │    weak ETag W/"v"     │ 1 min poll +    │
                       │ snapshot; rejects    │    If-None-Match→304   │ onInstalled     │
                       │ stale versions (409) │                        │ dNR → blocked.  │
                       └──────────────────────┘                        │    html         │
                                                                       └─────────────────┘
```

**Integration seams under test:** Manager→Sync write-through push · version monotonicity across services · ETag/304 consumer handshake · outage/pending/retry eventual consistency · SQLite persistence across restarts.

## Getting started

```bash
uv sync                      # or: pip install -r requirements.txt

# terminal 1 — Sync API first (Manager pushes to it)
uv run uvicorn services.sync_api.main:sync_app --port 3002

# terminal 2 — Manager API
uv run uvicorn services.manager_api.main:manager_app --port 3001

# try it
curl -X POST localhost:3001/rules -H 'content-type: application/json' \
     -d '{"domain": "https://www.reddit.com/"}'
curl -i localhost:3002/blocked    # note the ETag header; repeat with If-None-Match → 304
```

**Load the extension:** `chrome://extensions` → Developer mode → *Load unpacked* → select `extension/`. Chrome will ask to **read and change all your data on all websites** — accept it: `redirect` rules are only applied when the extension holds `host_permissions` for the affected hosts (see *Live finding* below). Within a minute (or on reload/browser restart) it fetches the list and blocked domains redirect to a local 🍅 page. On WSL2, Windows Chrome reaches the WSL servers via `localhost` forwarding out of the box.

## Running the tests

```bash
uv run pytest -m integration          # everything (~2s)
uv run pytest tests/integration/test_p3_negative.py -v   # one prompt's lineage
```

Four modules mirror the four prompt types; `test_smoke_real_servers.py` boots both services as real uvicorn subprocesses and drives them over actual HTTP.

## Prompt adjustment notes (what the real runs showed)

The headline result contradicts the usual story: **this model did not produce shallow output.** Every v1 run was verbose, well-formatted and technically competent — so "GenAI writes weak tests" is *not* what the experiment shows. What v1 lacked was **anchoring**: it spent real quality on capabilities this system doesn't have, and stayed silent about the mechanisms that actually hold the integration together.

- **P1:** v1 emitted *runnable* pytest + `jsonschema` code covering all 7 documented endpoints — zero hallucinated endpoints. Its two gaps were informative: nothing about stale-version rejection (the spec documents no `409`, so an unanchored prompt never asks for it), and `pytest.skip` when Sync was unreachable — a broken integration would have reported green. v2 added the cross-service rows (version +1, `304` empty body, stale push → `409`, idempotent replay) **and exposed a contradiction in my own prompt**: rule 3 demanded a stale-snapshot row while rule 4 forbade status codes absent from the spec. The model resolved it silently by breaking rule 4 — i.e. it tested an *undocumented* contract. The real defect is spec drift (`/internal/sync` should declare `409`), not prompt drift.
- **P2:** v1 produced ~30 scenarios in 8 areas — including ETag polling and eventual consistency — but invented auth tokens, credential rotation, expiring blocks, delta-sync responses, pagination and `*.example.com` wildcards, and never once named write-through push, monotonic version or `sync_status="pending"`. Most of it is untestable against this codebase. v2 produced 7 scenarios, each touching both services and ending with the seam it exercises, with **zero invented features** — and S7 predicted, before we hit it in production, that during an outage the consumer keeps getting `304` against a stale version and must keep enforcing the old list.
- **P3:** v1 generated ~50 cases of generic API hardening (JWT `alg:none`, multi-tenant cursor tampering, gzip bombs, Slowloris, IDOR) — none reachable in a two-service localhost demo — while `/sync/retry` semantics and version-vs-409 appeared nowhere; its own closing note only *advises* testing "against a real extension build". v2 returned 14 rows that are all cross-service with executable steps and a user-visible symptom ("a domain the user explicitly deleted starts blocking again"). Instructive slip: it wrote the snapshot key as `domains` instead of `sites`, so even a logically correct generated case must be checked against the spec before running.
- **P4:** the only prompt where v1 failed the textbook way: 20 real brand names (`facebook.com`, `youtube.com`…), zero edge inputs — nothing that could ever catch a normalization bug. Switching from "give me domains" to *inputs users actually paste* + machine-readable JSON with an expected normalized form made the output directly executable as a parametrized test. v2 returned exactly 12 accept / 8 reject rows, and its punycode is **correct** — verified against Python's `idna` (`café.com.br → xn--caf-dma.com.br`, `中国.com → xn--fiqs8s.com`). It also made an unrequested judgement call: accepting the IPv4 literal `192.0.2.1` because only IPv6 is rejected — right per our rules, but an inference rather than a stated requirement, so it now has its own test.
- **Live finding (post-suite):** no prompt type covered the *consumer-side* contract, and reality filled the gap. The decisive defect was a **permission**, not a schema: `declarativeNetRequest` grants implicit access only to `allow`/`allowAllRequests`/`block` rules, so **`redirect` rules need `host_permissions` for the affected hosts**. Without them Chrome accepts `updateDynamicRules` without error and `getDynamicRules` returns the rules, but the redirects are never applied — no match, no log, pages load normally. That is exactly the symptom that cost the most time: everything (Manager, Sync, ETag handling, rule dump) looked correct while the browser silently ignored the rules. A second trap on the way: JSON keeps only the **last** duplicate key, so merging a new `host_permissions` into the manifest without deleting the old one discards it — the fix would have been a no-op. Along the way four latent issues were hardened: relative `redirect.extensionPath`, redirect targets missing from `web_accessible_resources`, the deprecated `domains` field (matches the request *initiator*, not the target URL, so address-bar navigations never match), and omitting `resourceTypes` (silently excludes `main_frame`, i.e. top-level visits). A would-be **P5 prompt** ("generate contract checks between the Sync API response and the browser's declarativeNetRequest rule schema **and the permissions those rules require**") is the lesson: GenAI tested every seam we described, but seams we didn't describe stay untested until probed — and permissions are part of a consumer contract, not an implementation detail. Arguably the strongest argument for treating prompts as a *coverage plan*.
